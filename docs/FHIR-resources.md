# FHIR Resources

Verada Neurorehab Readiness uses a compact set of FHIR resources to support a clinically meaningful neurorehabilitation workflow. The goal is not to model every aspect of rehabilitation at once, but to use a focused resource set that supports patient review, daily readiness assessment, session planning, and write-back.

## Core Resources

### Patient

`Patient` is used for identity, demographics, and patient selection. It anchors all other resource relationships in the workflow.

### Encounter

`Encounter` represents the rehabilitation touchpoint or clinical session context. It helps link the day’s decision and therapy documentation to a specific interaction. 

### Device

`Device` identifies the source of physiological or therapy-related data, such as a remote monitoring or neurorehabilitation system. This is useful when observations are generated by multiple device types.

### Observation

`Observation` is central to the app. It can represent physiological data, symptom check-ins, fatigue, tolerance, adherence, and selected outcome measures before or after therapy.

### Condition

`Condition` captures diagnosis and active clinical problems relevant to rehabilitation planning, such as stroke-related deficits or other neurological impairments.

### CarePlan

`CarePlan` represents the rehabilitation pathway, therapy goals, and expected interventions. It provides the planned clinical context for the session decision. 

### ServiceRequest

`ServiceRequest` represents the therapy order or requested rehabilitation service. It complements the `CarePlan` and helps define why the session is taking place. 

### Procedure

`Procedure` captures what therapy was actually delivered during the session. It is useful for documenting session completion, modification, or deferral-related activity. 

### QuestionnaireResponse

`QuestionnaireResponse` can capture structured clinician or patient inputs such as tolerance, fatigue, readiness prompts, or symptom checklists.
## Optional Supporting Resources

- `MedicationStatement` for relevant medication context. 
- `AllergyIntolerance` for additional safety context. 
- `Communication` for follow-up instructions or clinician-to-team updates after the session. 

## Workflow Mapping

| Workflow step | Main resources |
|---|---|
| Patient selection | `Patient`, `Encounter` |
| Review baseline clinical context | `Condition`, `CarePlan`, `ServiceRequest`  |
| Review recent physiological state | `Device`, `Observation`  |
| Record readiness decision | `Encounter`, `Observation`, `QuestionnaireResponse`  |
| Document therapy delivered | `Procedure`, `Encounter`  |
| Write outcomes and follow-up | `Observation`, `Communication`, optionally `CarePlan` updates  |

## Implementation Notes

For the challenge version, it is better to keep the resource model small and coherent than to over-model the full rehabilitation domain. A clean implementation of a few core resources is more persuasive than a wide but inconsistent resource set.

Baseline and longitudinal context can still be represented, but they should support the daily readiness workflow rather than dominate the app design. In practice, that means using historical `Observation` and `Condition` context as inputs into today’s decision.
